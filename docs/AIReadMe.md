# 项目技术规范与 AI 参考文档

## 1. 项目概述

本项目为“基于大语言模型的文档理解与多源数据融合系统”，目标是构建一个能够自动解析多种格式文档（Word、Excel、Markdown、TXT）、抽取关键信息、语义匹配字段并自动填表的智能系统。系统需满足竞赛评测的高准确率与低响应时间要求。

### 核心能力
- 多格式文档统一解析
- 信息抽取（规则 + 模型 + 大语言模型）
- 字段语义匹配（向量相似度 + 规则校验）
- 知识池存储（一次解析，多次查询）
- 自动填表（Excel/Word 模板）

---

## 2. 系统架构与模块划分

系统采用模块化设计，各模块职责明确，通过统一数据接口通信。

| 模块 | 职责 | 关键技术 |
|------|------|----------|
| 文档解析模块 | 读取 .docx/.xlsx/.md/.txt，转换为统一 JSON 结构 | python-docx, pandas, openpyxl |
| 信息抽取模块 | 从文本中识别实体（金额、日期、项目名称等） | 正则表达式 + NER 模型 + 大语言模型 |
| 字段语义匹配模块 | 将模板字段与抽取实体进行语义对齐 | sentence-transformers, 向量相似度 |
| 知识池模块 | 存储实体信息，支持快速查询 | SQLite / MongoDB |
| 自动填表模块 | 根据模板生成 Excel 或 Word 结果文件 | openpyxl, python-docx |
| 系统整合与性能优化 | 提供 API 接口、缓存、并发、日志管理 | FastAPI, ThreadPoolExecutor |
| 前端与展示 | 文件上传界面、结果可视化、答辩材料 | Streamlit / Gradio |

## 3. 数据格式定义

所有模块间通信必须遵循以下 JSON 格式。

### 3.1 文档解析输出

```json
{
  "doc_id": "string",
  "paragraphs": ["string"],
  "tables": [[["string"]]],
  "raw_text": "string"
}
```

- `paragraphs`：文本段落列表
- `tables`：三维列表，第一维为表格序号，第二维为行，第三维为单元格内容
- `raw_text`：全文拼接文本（用于后续语义分析）

### 3.2 实体记录格式

```json
{
  "entity_type": "string",
  "value": "string",
  "source_doc": "string",
  "paragraph_index": "int",
  "confidence": "float"
}
```

- `entity_type`：实体类型，如“合同金额”“项目名称”
- `value`：归一化后的值（如金额转换为数字字符串）
- `source_doc`：来源文档 ID 或文件名
- `paragraph_index`：所在段落索引（从 0 开始）
- `confidence`：置信度，范围 0–1

### 3.3 知识池存储结构

数据库表或集合包含：
- `doc_id`
- `parsed_content`（JSON 格式）
- `entities`（实体列表）
- `create_time`

## 5. API 接口约定（后端）

系统需提供以下 REST API 供前端调用：

### 5.1 上传文档
- `POST /upload_docs`
- 输入：多文件（支持 .docx, .xlsx, .md, .txt）
- 输出：`{ "doc_ids": ["doc1", "doc2"], "message": "success" }`
- 行为：解析文档，抽取实体，存入知识池

### 5.2 上传模板并填表
- `POST /fill_template`
- 输入：模板文件（.xlsx 或 .docx）
- 输出：生成的结果文件（二进制下载）
- 行为：读取模板字段，语义匹配实体，生成填表结果

### 5.3 查询知识池（调试用）
- `GET /entities?doc_id=xxx`
- 输出：该文档的所有实体列表

### 6.2 代码风格
- **简洁高效**：代码应简洁明了，避免冗余和复杂的逻辑结构
- **自动格式化**：使用 `black` 自动格式化代码，确保代码风格一致
- **文档字符串**：函数、类、模块必须有完整的 docstring，说明功能、参数和返回值
- **类型注解**：所有函数和方法必须使用类型注解，提高代码可读性和可维护性
- **命名规范**：
  - 类名：使用驼峰命名法（如 `KnowledgePool`）
  - 函数和变量名：使用蛇形命名法（如 `extract_entities`）
  - 常量：使用全大写字母和下划线（如 `AMOUNT_PATTERN`）
- **缩进**：使用 4 个空格缩进，不使用制表符
- **行长度**：每行代码长度不超过 88 个字符（black 默认设置）
- **导入顺序**：标准库 → 第三方库 → 本地模块，按字母顺序排列

### 6.3 错误处理
- **异常捕获**：所有外部调用（文件读取、模型推理、网络请求）必须使用 `try-catch` 进行异常捕获
- **错误返回**：API 接口错误信息通过 JSON 格式返回 `{ "error": "description" }`，并设置相应的 HTTP 状态码（400 表示客户端错误，500 表示服务器错误）
- **日志记录**：关键操作和错误信息必须记录到日志，便于调试和问题定位
- **降级方案**：当核心功能（如模型加载）失败时，应提供合理的降级方案，确保系统能够继续运行

### 6.4 修改逻辑约定
- **保持原有逻辑**：修改 bug 时，应在不改变原有代码逻辑的前提下进行修复，确保功能一致性
- **最小化改动**：修改应尽可能小且精确，只针对问题所在的代码部分进行修改
- **测试验证**：修改后必须运行相关测试，确保修改不会引入新的问题
- **代码审查**：修改后的代码应进行代码审查，确保代码质量和风格符合规范
- **版本控制**：所有修改应通过版本控制进行管理，提交信息应清晰描述修改内容和原因

### 6.5 性能优化
- **缓存机制**：对于计算密集型操作，应使用缓存机制避免重复计算
- **并行处理**：对于批量处理任务，应使用多线程或异步处理提高效率
- **资源管理**：及时释放不再使用的资源，避免内存泄漏
- **模型优化**：使用轻量级模型和优化技术，提高推理速度

### 6.6 安全性
- **输入验证**：所有用户输入必须进行验证，防止恶意输入
- **文件处理**：处理文件上传时，应验证文件类型和大小，防止恶意文件上传
